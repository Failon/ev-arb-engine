# OddsPapi + The Odds API: трёхдневный research-пилот

Статус на 2026-11-17: авторизация обоих API и первые живые ответы проверены.
Трёхдневный сбор запущен 2026-11-17 18:18 UTC, завершение 2026-11-20 18:18 UTC.
Подтверждённых EV-сигналов пока нет: букмекерские settlement audits не завершены.
Никаких ставок, управления букмекерскими аккаунтами или покупки подписки.

## Что нужно один раз

1. Бесплатные аккаунты: https://oddspapi.io/us/sign-up и https://the-odds-api.com/.
2. Полученные API-ключи — только в секретах среды либо локальном `.env` в каталоге
   проекта. Файл уже исключён из Git. Формат (значения заменить локально):

```dotenv
ODDSPAPI_API_KEY=your_private_key
THE_ODDS_API_KEY=your_private_key
```

Не присылайте реальные ключи в чат, issue, PR или скриншот. Файл поддерживает
только эти две переменные, комментарии и обычные кавычки; команды не выполняет.
Переменные окружения имеют приоритет. Другой путь: `--secrets-file /private/keys.env`.

## Первый запуск: проверить доступ и получить реальные схемы

```bash
uv sync --frozen --extra dev
uv run ev-arb live-check
uv run ev-arb live-discover --config config/free-trial.json > live-discovery.json
uv run ev-arb live-run --config config/free-trial.json --once
uv run ev-arb live-report
```

`live-check` показывает только наличие ключей, без сети и раскрытия значений.
`live-discover` запрашивает каталоги bookmakers/markets OddsPapi и sports The Odds
API; локальный cache действует 24 часа. Исходные ответы сохраняются в `live-trial.db`.
Нельзя загружать эту БД или `live-discovery.json` в публичный GitHub: реальные данные
остаются локальными; в GitHub публикуются только обезличенные результаты проверки.

Конфигурация содержит пустые `papi_books`, `odds_books`: **сбор работает, но до
проверки правил EV не рассчитывается**. `papi_market` уже проверен по живому
каталогу: soccer/101, fulltime, 1x2, outcomes 101/102/103.
Первый проход показывает фактически доступные БК и причины исключения. После
получения ответов разработчик проверяет, какие из них — именно российские версии,
какой рынок является полным moneyline/90-minute result, и правила его расчёта.
Присутствие имени в каталоге не подтверждает доступность счёта из России.

## Конфигурация проверенных рынков

Перед началом многодневного окна заполните `config/free-trial.json`:

- `papi_books` / `odds_books`: provider slug → `canonical_id` исходного букмекера и
  региона, `rules` (ruleset/overtime/abandonment), `evidence` (ссылка и дата проверки),
  `commission`, `sports` (например `["soccer"]`), `accessible_from_russia`.
- `papi_market`: `market_id`, `sport_id=10`, `outcome_ids` с ключами в порядке
  home/draw/away и подтверждёнными ID исходов, `evidence` проверки каталога `/markets`.
  Нельзя подставлять демонстрационные ID из документации вместо ответа вашего API.
- Разным reseller-slugs одного букмекера задайте один canonical_id; такие копии
  не увеличивают reference_count. Одинаковый ruleset допустим лишь для действительно
  одинаковых проверенных settlement policies.

Не нужно придумывать правила ради сигнала. Непроверенные БК остаются в inventory,
неизвестные рынки и extra outcomes не нормализуются. Проверка правил проводится
для каждого вида спорта; футбольная конфигурация не применяется к теннису/баскетболу.
Provider-native события анализируются отдельно: автоматического склеивания похожих
названий между OddsPapi и The Odds API нет. OddsPapi сверяет ID, участников, спорт и
начало odds с ранее полученным fixture; несовпадение помещает ответ в карантин.

`accessible_from_russia` — явная отметка подтверждённой доступности конкретной
версии, не вывод из географии API. EV-кандидаты сохраняют эту отметку; эталон с
неподтверждённой доступностью не превращается в доступный счёт для исполнения.

## Три дня сбора

```bash
uv run ev-arb live-run --config config/free-trial.json
```

По умолчанию: 3 дня, один проход в час, до 200 запросов OddsPapi и 400 кредитов
The Odds API на весь локальный эксперимент. Все команды используют одну БД и
одни счётчики. 401/403/429 и нулевой остаток приостанавливают запросы; 429 учитывает
Retry-After, без него пауза сутки. Ошибки тоже резервируют квоту, повторы автоматически
не выполняются. Расход и блокировки сохраняются между перезапусками. Ключ The Odds
API передаётся в официальном `x-api-key` header; OddsPapi требует query apiKey.
HTTP debug-логи должны быть выключены. Возможные эхо ключей очищаются до записи.

OddsPapi раз в шесть часов ищет предстоящий футбол на сутки и выбирает одно событие
на проход по кругу; читает все предлагаемые для этого события БК одним запросом.
Можно ограничить турниром `papi_tournament_id`; null означает все футбольные турниры.
The Odds API получает пакет `upcoming`, регион eu, рынок h2h; альтернатива — soccer_epl.
Только аудированные виды спорта и полные рынки проходят к сигналам.

Верхняя оценка для стандартных 72 проходов: 84 запроса OddsPapi (72 odds + 12
обновлений fixtures), 72 кредита The Odds API. Первичная инвентаризация добавляет
2 запроса OddsPapi и консервативный локальный резерв 1 для sports The Odds API
(провайдер сам не тарифицирует sports). Фактический расход зависит от наличия
событий/ошибок; заголовки The Odds API сверяются с локальным расходом. Квота общая
для аккаунта: не запускайте другие сборщики с теми же ключами без общего бюджета.
Другие интервалы могут исчерпать локальный предел раньше трёх дней; тариф не меняется.

Окно начинается с первого live-run, фиксируется и не продлевается перезапуском.
`--once` тоже начинает окно: используйте после настройки проверенных правил либо
осознанно запускайте пилот только для инвентаризации. После начала параметры окна, источников и бюджета заморожены. Можно добавлять
новые подтверждённые bookmaker audits и один раз заполнить пустой market audit:
каждая версия записывается в БД и помечает будущие проходы. Ранее принятые правила
нельзя менять или удалять. После изменения конфигурации процесс нужно перезапустить;
срок и расход при этом сохранятся. История не пересчитывается задним числом.
Не удаляйте БД ради сброса квот. Ctrl+C сохраняет прогресс; та же команда продолжает
существующее окно, не повторяет уже занятый временной слот.

## Где смотреть результат

```bash
uv run ev-arb live-report > live-report.json
```

Отчёт работает без сети и ключей. Показывает окно, число проходов, фактический
inventory БК, локальный расход, состояние источников, свежие/устаревшие котировки,
причины отклонения и число уникальных снимков-кандидатов. БД содержит исходные
ответы и детали сигналов для проверки. Новое время получения того же снимка не
увеличивает число сигналов. Неизвестные исходы/правила не превращаются в нулевую прибыль.

OddsPapi `changedAt` — время последнего изменения цены, не heartbeat наблюдения.
Мы используем самый старый changedAt полного набора исходов и явно отмечаем это
в health; метаданные fixture.updatedAt не подменяют свежесть цены. Возраст >30 секунд
исключается. Стабильные линии поэтому могут консервативно отбрасываться; частый
запрос не делает их временную метку свежей. У The Odds API используется last_update
рынка. Это исследование доступности/качества, а не быстрый непрерывный live-feed.

+EV требует трёх разных исходных букмекеров, является оценкой consensus с haircut.
При двух и более совместимых БК дополнительно фиксируется `theoretical_price_gap`
по сумме обратных effective odds <1. Ликвидность остаётся неизвестной (0), поэтому
это не исполнимая вилка и не прогноз прибыли. Реальных и виртуальных исполнений в
этом пилоте нет; profit/CLV остаются null до отдельной модели расчёта и closing data.
Три дня сигналов сами по себе не доказывают доходность.

## Фоновый запуск

Команда работает, пока работает компьютер/сервер. Сбор запущен фоновым процессом в текущей облачной среде, состояние — в
`live-trial.db`, локальный журнал — `live-trial.log`. Остановка/приостановка среды
приостанавливает сбор; непрерывная доступность этой среды на три дня не подтверждена. Для постоянно включённого
Linux-сервера есть `deploy/ev-arb-live.service.example` для пользовательского systemd:
он предполагает checkout в `~/ev-arb-engine`, ключи в `~/.config/ev-arb/keys.env`,
БД в `~/.local/state/ev-arb/live-trial.db`. Создайте эти каталоги, ограничьте доступ
к файлу ключей, скопируйте unit в `~/.config/systemd/user/ev-arb-live.service`, затем
запустите `systemctl --user daemon-reload` и `systemctl --user start ev-arb-live`.
Для работы после logout на сервере должен быть настроен user lingering.
По окончании окна процесс завершится; успешное завершение не перезапускается.
Шаблон не устанавливался и не проверялся на живом сервере в этой задаче.
